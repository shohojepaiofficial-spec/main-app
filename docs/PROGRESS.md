## 2026-09-14 (Promo codes — manual entry, shareable links, and banner-driven discounts, unified)
Three asks in one request turned out to be the same underlying feature: a promo code system where a code can be applied either by typing it in, or automatically from a URL — which covers "share a link that gives a discount" and "a banner button triggers a discount" for free, since **banners already support arbitrary link URLs** (`primaryCta.href`/`secondaryCta.href`, no schema change needed there at all). Pointing a banner's button at `/shop?promo=CODE` (store-wide) or `/shop/<productId>?promo=CODE` (one product) is the entire "banner-driven cost cut" feature.

- **Backend**: new `PromoCode` model (`code`, `discountType: "percentage" | "flat"`, `value`, `scope: "all" | "product"` + optional `product` ref, `isActive`, optional `expiresAt`). Admin CRUD at `/api/promo-codes` (needs the new `promotions:manage` permission — added to the delegable permission list alongside products/orders/banners). `POST /api/promo-codes/validate` is **public** (no auth) — both the cart's manual entry box and a code auto-applied from a link need to work for guests. It only confirms a code's terms (type/value/scope); the actual discount math happens client-side against the cart, same as the rest of the cart (still no backend order/checkout to check it against — see Known follow-ups).
- **Cart** (`useCartStore.ts`): added `promo: AppliedPromo | null`, `applyPromo`/`clearPromo`, and `discountAmount()`/`grandTotal()` alongside the existing `totalPrice()` (now explicitly the pre-discount subtotal). A `scope: "product"` promo only discounts that one line item, and only if it's actually in the cart (a shared product-specific link doesn't just discount whatever's in your cart). `CartModal` now has a promo code input (or, once applied, an "applied" chip with a Remove button), a Subtotal/Discount/Total breakdown.
- **Auto-apply from a link**: new invisible `views/PromoAutoApply.tsx`, mounted on `/shop` and `/shop/[id]` (both already read `searchParams` server-side, so passing `promo` through costs nothing extra — deliberately did *not* reach for `useSearchParams()` client-side here, which would've opted the whole public route into needing a Suspense boundary). A bad/expired code in a shared link fails silently rather than blocking the page.
- **Admin**: `/admin/promotions` (`views/AdminPromotionsView.tsx` + `PromoCodeFormModal.tsx`, gated by `promotions:manage` like Products/Orders/Banners) — create/edit/delete codes, see each one's status (Active/Inactive/Expired), and a one-click "copy share link" button per code that builds the right `?promo=` URL depending on its scope.

### Known follow-ups (new)
- **No usage-limit enforcement** (`maxUses`/`usedCount`) — deliberately left out rather than half-built, since there's no order/checkout-completion event yet to hook an increment into; adding a usage cap now would either not decrement anywhere or decrement on every re-validation (wrong either way).
- A `scope: "product"` code's JSON-LD/structured-data implications weren't touched — that's a separate, smaller follow-up if it matters for SEO on a discounted product page.
- The product picker in the promo code form only lists the first 48 products (one page) — fine at the store's current size, would need real search-as-you-type if the catalog grows past that.

## 2026-09-14 (Fixed: coadmin's granted access wasn't showing up)
Real bug, not just a caching nuance: `register`/`login`/`oauthSync` in `authController.ts` never included `permissions` in the response `user` object at all — only `id`/`name`/`email`/`role`. So a coadmin's `permissions` was `undefined` from the moment they logged in, regardless of what was actually granted in the database, and every `hasPermission()` check on the frontend (which is what `DashboardSidebar` uses to decide which admin links to show) was silently always false. This is why granting a coadmin `products:manage` never made "Manage Products" appear — it was never sent to their browser in the first place, not a staleness issue.

- Fixed by adding `permissions` (and `image`, missing from `register`/`login` too) to all three response shapes.
- Also added `GET /api/auth/me` (protected) and a `useRefreshUser` hook (mounted once in `app/providers.tsx`, alongside the existing OAuth bridge) that refreshes the cached `user` on every app load. This covers the *other*, real remaining gap: an admin changing a coadmin's access **after** that coadmin already has a browser session open — the API already enforces the change immediately (it re-checks the DB on every request, see `middleware/auth.ts`), but the cached frontend `user` used for sidebar visibility didn't update until a fresh login. Now a normal page refresh is enough, not a full log-out/log-in.
