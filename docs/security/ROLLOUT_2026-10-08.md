# Security implementation and rollout

Updated: 2026-10-09. This records local changes for SEC-04 through SEC-13. Nothing in this pass was deployed, and no production database records, provider settings or backups were changed. Read the queue for current completion status. Unit tests use simulated persistence; they do not establish real MongoDB race behavior.

## Application changes

- **SEC-04:** customer/staff/bulk/payment status changes share a conditional MongoDB transaction. Cancellation and ordinary/variant/pre-order inventory restoration commit together. Cancelled orders cannot reopen; missing inventory records stop cancellation for review. Bulk operations commit one order at a time. Pending bKash orders require authoritative failure before cancellation; cancelling a recorded paid bKash order flags refund review.
- **SEC-05:** customer and manual checkout require an account-scoped idempotency key backed by a unique index. Matching retries return the original order; changed payloads conflict. Carts allow 50 distinct lines and 100 units per line. IP/account/quote limits bound repeated work. Online reservations have a 30-minute deadline; a one-minute worker examines batches of 50, rotating older checks behind unchecked records. Unknown gateway outcomes retain inventory and appear as payment review in the admin UI. Definitive failure releases once; verified success checks the amount and transaction ID. No-payment-ID reservations release on expiry. Gateway calls have timeouts.
- **SEC-06:** shared-cart lines are authoritative, expire after seven days, and are claimed within the order transaction. Altered lines or competing claims fail. COD fulfills immediately; online payments claim first and fulfill on verified success. Failed online payments release only their own unfulfilled claim. Cancelled COD links stay fulfilled; create a new link to try again. Legacy links without expiry are invalid rather than silently permanent.
- **SEC-07:** upgraded Multer, Next.js and compatible transitive dependencies; added sharp for decoding and zod for runtime validation. Frontend production audit is clean. Backend retains PM2-chain advisories described below.
- **SEC-08:** browser API requests use `/api/backend/...` on the frontend origin. Access/refresh secrets live in server-set HttpOnly cookies, Secure with `__Host-` names in production, SameSite=Lax and Path=/. JavaScript cookies now contain unsigned UI markers and cached user data only. The backend rejects these markers as credentials. Old secret-bearing JavaScript cookies are cleared on hydration, requiring sign-in. The proxy injects the real bearer credential server-side, strips credentials from JSON, validates mutation Origin plus a custom header, and blocks the internal OAuth exchange. NextAuth retains backend credentials in its encrypted HttpOnly session; the browser redeems the handoff through server-side refresh. Auth mutations, refresh and logout share browser session locking where Web Locks are supported. Older browsers without Web Locks retain single-tab coordination; cross-tab races require browser verification.
- **SEC-09:** uploads decode and re-encode to WebP before Cloudinary/local storage. Invalid/spoofed/truncated files, animated files and images over 20 million pixels or 8000 pixels on either axis are rejected. Static JPG/PNG/WebP/GIF are supported. The upload policy is now four MB combined with form fields through the frontend proxy, below Vercel's 4.5 MB limit; the browser rejects oversized forms before transfer. Five files remain allowed. Server per-file limits are four MB and include field/part limits, at most eight concurrent multipart requests per process and four concurrent decodes.
- **SEC-10:** controller input allowlists, scalar and ID checks, bounded queries, strict checkout/product schemas and operator/dotted-key rejection cover JSON and multipart controller inputs. Product writes reject unknown writable fields; retained images must already belong to that product. Intentional database operators remain server-built.
- **SEC-11:** production rate-limit counters use MongoDB across instances, with TTL cleanup and fail-closed behavior. Default X-Forwarded-For trust is disabled. The Vercel frontend signs its platform-verified client IP with the shared internal secret; the API accepts it only with a fresh valid signature. Other hosting topologies need explicit verification/configuration. JSON/multipart/request time budgets are bounded. Edge protection, origin restrictions, bot challenges and staging load verification remain outstanding.
- **SEC-12:** unexpected 5xx JSON is generic; access logs omit query strings. New passwords require 12 characters and at most 72 UTF-8 bytes; existing passwords can still sign in. The user selected email verification at checkout only, retaining sign-in and resend access. New pending TOTP secrets use versioned AES-256-GCM encryption; confirmed secrets retain that ciphertext. Migration/rotation is provided as an explicit command, not run automatically.
- **SEC-13:** added a read-only configuration preflight and the operational evidence checklist below. Actual production controls remain unverified.

## Release prerequisites

1. Release both applications together over HTTPS. Keep `INTERNAL_API_SECRET` identical and private in frontend/server environments. Set frontend `AUTH_SECRET`. Preserve `NEXT_PUBLIC_API_URL` as the real backend URL; the browser proxy is selected automatically. Verify Google callback domains and API URLs. Public server-rendered data still uses the backend directly.
2. Configure `TOTP_ENCRYPTION_KEY_ID` and `TOTP_ENCRYPTION_KEYS` in the server secret manager. The latter is a JSON object mapping key IDs to independently generated 32-byte base64 keys. Keep these separate from JWT and database credentials. Do not paste keys into Markdown, chat or committed files.
3. During a controlled migration window, enable `TOTP_ALLOW_LEGACY_PLAINTEXT=true` and run `npm.cmd --prefix server run security:encrypt-totp`. This modifies factor records: run on staging first, confirm a recoverable backup and coordinate production execution. It uses conditional writes, encrypts existing active factors and invalidates pending setups. Then disable the legacy flag. Keep old encryption keys until all ciphertext and retained backups have migrated; re-run the command with a new active key to rotate. Do not roll back to code unable to decrypt ciphertext.
4. Provision the Order unique `{ user, idempotencyKey }` partial index and reservation index, SharedCart expiry index, RateLimitCounter `_id`/expiry TTL indexes and existing AuthSession indexes. Use the deployment's index-management process. A TTL index never releases reserved inventory; the reconciliation worker does that. Existing manual orders have no idempotency key and remain outside the unique constraint. New manual keys are prefixed with the staff account ID.
5. Review legacy online pending orders individually: they have no reservation deadline and are deliberately excluded from automatic release. Query the gateway before deciding on cancellation. Old shared-cart links without an expiry must be recreated. No migration of historical orders/links was run.
6. Verify the actual ingress topology. `TRUSTED_PROXIES` accepts a comma-separated IP/CIDR allowlist; leave it empty unless the deployment proves which proxies are trusted. The signed Vercel client-IP mechanism is separate. Preserve provider network protection for both storefront and API. Protect the public API origin with provider controls while allowing required public catalog/payment callback traffic.
7. Run `npm.cmd --prefix server run security:preflight` in the intended environment. It prints boolean checks and unverified controls only. A passing preflight does not establish database permissions, MFA, DDoS protection or recoverability.

## Required staging checks

- With a real replica set, race customer/staff/bulk/payment cancellations and checkout retries. Assert one reservation/restock, unchanged counters on rollback and no reopening of a cancelled order. Include deleted variants and pre-order counters that require manual review.
- Race two payers on a shared link; test expired/legacy links, altered quantities, COD cancellation, gateway failure, unknown outcomes, worker restart and payment success arriving after release. Verify merchant sandbox response status spellings, currency/amount semantics and transaction IDs before enabling live payments. Unknown statuses intentionally remain held for review.
- Verify local/Google/staff-2FA login, factor management, refresh, logout/all-device logout, password reset, multiple tabs, late responses and browsers without Web Locks. Confirm no actual JWT signatures or refresh credentials are in JavaScript-readable cookies, storage or NextAuth session JSON. Cross-site mutations must fail. On deployment, old browser sessions must sign in again.
- Verify unverified local accounts can sign in/resend verification but cannot check out; verify a clicked confirmation allows checkout. Confirm existing Google accounts are marked verified. Test UTF-8 password boundaries and login with an existing shorter password.
- Test normal product/banner/profile uploads, corrupt/spoofed files, dimensions, animation rejection, retained image ownership and multipart concurrency. Confirm the image policy is communicated in upload forms.
- Verify counters across two app instances, counter-store failure, signed client-IP tampering, direct API ingress and shared-mobile-network clients. Use a small agreed staging load with duration/concurrency/stop thresholds. Do not load-test the live store or gateway.

## Residual dependency advisories

After compatible fixes, the frontend production audit reports **0** vulnerabilities. The backend retains **8 high**, **0 critical**, **0 moderate** production findings through PM2: `basic-ftp -> get-uri -> pac-proxy-agent -> proxy-agent -> pm2`, `braces -> chokidar -> pm2`, and `js-yaml -> pm2`. These are affected dependency packages, not eight demonstrated application exploits. Frontend development tooling also retains a braces/ESLint chain, excluded from the production count.

The audit proposes downgrading PM2 to 5.3.1 with `--force`; that breaking change was not applied. PM2 remains a supported optional process supervisor in this repository. Resolve with a compatible upstream release or an explicit deployment-supervisor migration, then repeat audits and startup/restart checks. Do not claim SEC-07 fully closed while these findings remain. No evidence was collected that user request data reaches the affected PM2 parsing functions.
