# Security queue verification - 2026-10-08

The queue is broadly supported by the current source. There are real application risks, particularly session revocation, inventory consistency and shared-cart fulfillment. This review does not establish that the deployed site has been compromised. The deployed revision, hosting protections, production database permissions and incident logs were not inspected. Local fixes provide no production protection until deployed.

## Dependency audit interpretation

The read-only registry audits completed on 2026-10-08 after the sandbox initially blocked registry access:

| Package | Critical | High | Moderate |
| --- | ---: | ---: | ---: |
| Backend production dependencies | 1 | 8 | 1 |
| Frontend production dependencies | 1 | 2 | 0 |

These count affected packages, including packages inheriting severity from a transitive dependency, not distinct exploitable endpoints.

- The [Next.js advisory](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j) concerns attacker-controlled SVG inputs to Node.js `next/og` ImageResponse. No `next/og` or `ImageResponse` usage was found in frontend source. That specific attack path was not identified here; the dependency still needs updating under SEC-07.
- The [proxy-addr advisory](https://github.com/advisories/GHSA-jqcg-44mw-7w3h) concerns particular IPv6 trust-subnet configurations. The app currently sets numeric `trust proxy: 1`. The advisory's configuration was not found, but the one-hop assumption still needs deployment verification.
- The [Multer advisory](https://github.com/advisories/GHSA-3pph-fpjx-jg34) concerns orphaned `diskStorage` writes. This app uses `memoryStorage`; that specific storage path was not identified. Memory/concurrency limits and image-content validation remain separate concerns.
- Backend high counts include PM2's dependency chains. Frontend high findings include sharp and source-map-js. Their deployment reachability still needs investigation during SEC-07. Do not apply `audit fix --force` blindly.

## SEC-02 acceptance evidence

Recent authentication is a server-signed timestamp added after successful password verification or a new server-validated Google OAuth exchange. It is carried unchanged through the second-factor challenge; JWT issuance or password recovery cannot renew it. Google can reuse its own SSO session: this application does not claim to force Google to ask for its password again. Existing backend sessions alone cannot create a fresh timestamp.

All factor-management operations require that timestamp to be less than five minutes old. Initial enrollment and replacement use separate endpoints. Replacement/disable also require a current TOTP or unused backup code. The old authenticator remains active until the new code is confirmed; confirmation rotates backup codes. Pending setup expires, is bound to the exact access token, and cannot complete if the active factor changed. Unique access-token IDs distinguish separate sign-ins in the same second.

Conditional writes protect enrollment, replacement and disabling against stale reads. Backup-code consumption is conditional across management and login requests. Failed attempts count toward the existing shared per-account factor-management limit. Sensitive setup/backup-code responses use `Cache-Control: no-store`.

Local verification: 263 backend tests, 58 frontend tests, both builds, changed frontend ESLint and whitespace checks passed. Coverage includes customer rejection, old/future/missing authentication timestamps, client-supplied timestamp spoofing over HTTP, initial enrollment, admin/coadmin replacement, wrong old/new codes, expired/foreign-session setup, concurrent conditional-write rejection, backup-code reuse, password recovery and delayed challenge exchange. HTTP route coverage now includes 70 private routes and 48 staff routes. Model writes are mocked: this is not a live MongoDB concurrency test or a live Google/browser test.

Deployment checks: release both apps, sync translations, sign in again for factor management, verify initial setup and replacement for password and Google staff accounts, cancel replacement and confirm the old authenticator still works, then confirm replacement and verify only the new authenticator/new backup codes work. Verify throttling and five-minute expiry on staging. Keep SEC-03 as the next implementation task; existing sessions are not yet revoked when passwords or factors change.

Design reference: [OWASP guidance on changing MFA factors](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html).
