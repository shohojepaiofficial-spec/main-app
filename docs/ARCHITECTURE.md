# Architecture & Conventions

This project follows an MVC (Model-View-Controller) pattern in both `server/` and `frontend/`. Every new feature must map onto these layers — no logic embedded directly in routes or page files.

## Backend (`server/`)

Classic MVC:

- `src/models/` — Mongoose schemas only. No business logic beyond validation/hooks.
- `src/controllers/` — request handlers. Parse input, call models, shape the response. No route wiring here.
- `src/routes/` — Express routers. Map HTTP verb + path to a controller function. No logic.
- `src/middleware/` — cross-cutting concerns (auth, error handling).
- `src/utils/` — stateless helpers (email, uploads).

## Frontend (`frontend/src/`)

Next.js App Router doesn't have a native MVC split, so it's mapped explicitly:

- `models/` — TypeScript types and zod schemas. The shape of data, nothing else.
- `services/` — pure functions that talk to the backend API (axios calls). No React, no state.
- `controllers/` — custom hooks and zustand stores. All state and business logic (what happens on click, what to fetch, when). Calls into `services/`.
- `views/` — presentational components only. Receive data/handlers as props (or from a controller hook) and render UI. No direct API calls.
- `components/ui/` — generic, reusable UI primitives with no domain knowledge (Modal, Dropdown, Button). Not part of the MVC domain layers; shared building blocks for `views/`.
- `app/` — Next.js routing shell. A page file should be a thin composition of a controller hook + a view — it should not contain business logic itself.

### Rule of thumb when adding a feature

1. Define/extend the type in `models/`.
2. Add the API call in `services/`.
3. Add a hook in `controllers/` that uses the service and exposes state + handlers.
4. Build the UI in `views/`, consuming the controller hook.
5. Wire it into a page under `app/` — the page should be nearly empty logic-wise.

### Fetching in a `controllers/` hook: avoid `react-hooks/set-state-in-effect`

This project's `eslint-config-next` version ships a React Compiler lint rule that flags calling a `useState` setter — even transitively, through a named callback like `const load = useCallback(async () => { setX(...) }, [])` then `useEffect(() => { load() }, [load])` — because it can statically see straight through that indirection. It does **not** flag a setter called from inside a `.then()`/`.catch()`/`.finally()` callback that's chained inline in the effect, since that's a genuine deferral rather than a same-tick call. So a client-only fetch-on-mount hook (see `useAdminUsers.ts`, `useAdminProducts.ts`) should look like:

```ts
useEffect(() => {
  let ignore = false;
  someService.getThing()
    .then((data) => { if (!ignore) setThing(data); })
    .catch(() => { if (!ignore) toast.error("..."); })
    .finally(() => { if (!ignore) setIsLoading(false); });
  return () => { ignore = true; };
}, []);
```

Similarly, prefer mounting a fresh subcomponent (`key={...}`) over a `useEffect` that resets local state when a prop changes — see `ProductFormModal.tsx`'s `ProductForm`.

### Any zustand store using `persist` needs `skipHydration` + a manual rehydrate

Zustand's `persist` middleware reads `localStorage` **synchronously the moment the store module evaluates in the browser** — before React can guarantee the client's first render agrees with the server-rendered HTML (which never has localStorage access, so it always renders that store's plain initial state). A returning visitor whose persisted value differs from the default (items in their cart, a non-English `locale`, etc.) gets a real hydration mismatch the instant any component renders differently based on it — this bit both `useCartStore` (the navbar's cart-count badge) and `useUIStore` (`LanguageSwitcher`'s `<select value={locale}>`), see `docs/PROGRESS.md`'s 2026-09-15 "cart-count badge hydration mismatch" entry for the full story.

The fix, applied to both and required for any future `persist`-backed store: pass `skipHydration: true` in the persist config, and call `use<Whatever>Store.persist.rehydrate()` once in `app/providers.tsx`'s existing mount `useEffect` (alongside `useAuthStore`'s own `hydrate()` call — same file, same effect, same idea: keep the first client render in agreement with the server, then load the real persisted value immediately after mount). This is the exact same root-cause class as `useAuthStore.isAuthenticated()`'s documented hydration fix elsewhere in this file, just via zustand's built-in persistence instead of a manual cookie read.

### Server-rendered data vs. client state

For a page that just needs to *display* data (a product list, a hero banner), call the `services/` function directly from an `async` Server Component page and pass the result down as props to a `views/` component. Don't fetch it again in a `controllers/` hook with `useEffect` — that causes an empty-then-populated flash and is worse for SEO/first paint. Reach for a `controllers/` hook + client-side fetch only when the data is genuinely client-only (depends on a cookie/localStorage, needs to refetch on a client-side interaction, etc.) — e.g. cart and auth state. `useHeroSlider` follows this: the page fetches slides server-side and passes them in; the hook only owns the (inherently client-side) autoplay/index state.

### Route groups

- `app/(public)/` — storefront pages, wrapped in `layout.tsx` with the `Navbar`, `AuthModal`, and `CartModal`.
- `app/(protected)/` — account pages (Dashboard/Orders/Settings), wrapped in `layout.tsx` with `DashboardSidebar` and guarded by `controllers/useRequireAuth.ts` (client-side redirect if not authenticated — no server-side session check yet).
- Root `app/layout.tsx` only holds the html/body shell, fonts, `Providers`, and `Toaster` — no site chrome, so each route group controls its own.

### Navbar is `fixed`, not `sticky`

`Navbar`'s `<header>` is `position: fixed` so it reserves no layout space on its own — every page under `app/(public)/` is responsible for padding its own content below it:

- `Navbar` measures its own real rendered height (via `ResizeObserver`) and publishes it as `--navbar-height` on `document.documentElement`, with a static fallback in `globals.css` for the pre-hydration paint.
- Every public page offsets its content with `pt-[var(--navbar-height)]` (or `pt-[calc(var(--navbar-height)+Npx)]` for extra breathing room) — see the homepage (`app/(public)/page.tsx`) and `PlaceholderPage`'s `offsetForFixedNavbar` prop (default `true`). Pages under `app/(protected)/` don't render the public `Navbar` at all, so they pass `offsetForFixedNavbar={false}`.
- The navbar itself is a permanent light glassmorphism panel (`bg-surface/70` + `backdrop-blur-md`, slightly more opaque with a shadow once scrolled) with plain `text-foreground` — deliberately *not* transparent-with-white-text-over-a-photo. That was tried and reverted: a hero photo's brightness at its own top edge is unpredictable (skies, white backgrounds, etc.), so white nav text over it isn't reliably legible. Don't reintroduce per-page/per-scroll text-color branching in the navbar for this reason.

### Theming

Colors and fonts are CSS variables in `globals.css` (Tailwind v4 `@theme inline`), not hardcoded utility colors. Use `bg-primary` / `text-foreground` / `bg-surface` / `text-muted` / `border-border` etc. — never `bg-black`, `text-neutral-500`, `dark:bg-neutral-800`, and the like — so the palette (and dark mode) can change from one file.

## SEO

Every public page must ship with its own metadata — this is a standing requirement, not a one-off:

- Every page under `app/(public)/` exports its own `export const metadata: Metadata` (title + description), **or**, for a dynamic route (`app/(public)/shop/[id]/page.tsx`), an `async generateMetadata({ params })` that fetches the entity and derives title/description/OG image from it (falling back to a plain "Product not found" title when the fetch comes back empty — the page itself then calls `notFound()`). Never leave a page to silently inherit the root layout's generic title — duplicate `<title>`/description across pages is a real ranking penalty. The root `app/layout.tsx` sets a `title.template` (`"%s | New Ecommerce"`), so a page only needs to set its own short `title`; the site name is appended automatically. The one exception is the homepage (`app/(public)/page.tsx`), which deliberately has no metadata export so it keeps the root's full branded title instead of running through the template.
- A page for a single real-world entity (a product) should also emit JSON-LD structured data (`<script type="application/ld+json">` with a `schema.org` `Product`/`Offer`/`AggregateRating` payload) — see `app/(public)/shop/[id]/page.tsx`. This is what backs the rich results (price, stock, star rating) search engines show, on top of the plain title/description.
- `app/sitemap.ts` is `async` and includes dynamic entries, not just the static route list — it paginates through `productService.getProducts()` to list every `/shop/[id]`. When a new *kind* of page-per-entity is added (e.g. a future `/categories/[slug]`), extend `sitemap.ts` the same way rather than leaving it static-only.
- Every page under `app/(protected)/` exports `metadata.robots = { index: false, follow: false }` — account pages are behind a login and must never be indexed.
- `app/robots.ts` and `app/sitemap.ts` are generated from a single `PUBLIC_ROUTES`-style list / explicit disallow list — when a new public route is added, add it to `sitemap.ts`; when a new protected route is added, add it to `robots.ts`'s `disallow` and give the page its own `noindex` metadata (belt and suspenders).
- `NEXT_PUBLIC_SITE_URL` in `frontend/.env.local` backs `metadataBase`, Open Graph `url`, and the sitemap/robots base — update it to the real domain before deploying.
- Use one `<h1>` per page (the hero slide title or the page's own heading), real `<Link>`/`<a>` elements for navigation (not `onClick`-only `<div>`s), and meaningful `alt` text on images — already the pattern in `HeroSlider`.

## Checkout & Orders

- **Cash on Delivery or bKash.** "Place order" always creates a real `Order` immediately at `status: "pending"` and decrements stock (inside the same transaction as everything else below). For `cod` that's the whole flow — the customer pays when it arrives. For `bkash`, `createOrder` then calls bKash's Tokenized Checkout API (`integrations/bkash.ts`) to start a payment session for that order's `totalAmount` and responds with `{ ...order, bkashRedirectUrl }`; the frontend sends the browser straight there (no "order placed" screen yet — payment isn't confirmed). If starting the bKash session itself fails, the order is cancelled and its stock restored immediately rather than left as an unpayable "pending" order.
- **Checkout requires login** — `/checkout` lives under `app/(protected)/`, same as Dashboard/Orders/Settings, guarded the same way (`useRequireAuth`, client-side redirect). There's no guest checkout.
- **The server is the only source of truth for money.** `POST /api/orders` (`orderController.ts#createOrder`) takes only `{productId, quantity}` per line plus the shipping address — never a client-submitted price or delivery fee. It re-fetches each `Product`, validates stock, computes `itemsTotal`/`deliveryFee`/`discount` itself, and only then decrements stock (after *every* line validates, so a bad item further down the cart can't leave earlier ones partially deducted).
- **Delivery fee** is one flat fee per distinct product line (not per unit, not per order) — summed from whichever of a product's `deliveryFeeInsideCity`/`deliveryFeeOutsideCity` applies, based on comparing the shipping `zila` to `STORE_CITY`. `server/src/utils/store.ts` is the one place this is actually defined; the frontend has no hardcoded copy of it — `GET /api/config` (public) serves it, and `frontend/src/services/configService.ts#getStoreCity()` fetches it once per page load in whichever server component needs it (`/`, `/shipping`, `/terms`, `checkout/page.tsx`, `dashboard/page.tsx`), passed down as a `storeCity` prop from there — `lib/delivery.ts#isInsideStoreCity`/`calculateDeliveryTotal` both take it as a parameter rather than importing a constant. This used to be a second hardcoded copy in `frontend/src/lib/seo.ts`, flagged for a while as a real but low-priority duplication risk before being fixed this way (a network dependency instead of a monorepo/shared-package restructuring, since the two projects deploy independently to Vercel/Railway).
- **Location capture**: Zila (district) and Upazila (sub-district) are cascading `<select>`s sourced from `frontend/src/lib/bangladeshGeo.ts` (64 districts / 494 upazilas, from the `nuhil/bangladesh-geocode` dataset, MIT) — only the final house/road/area line is free text. `views/ZilaUpazilaFields.tsx` is the shared presentational piece (takes an optional `disabled` prop); `User.deliveryLocation` (a saved default) and `Order.shippingAddress` (a per-order snapshot) both use this same three-field shape.
- **Reusing a saved delivery address at checkout**: when `User.deliveryLocation` is fully set, `CheckoutView` shows a radio choice — "Use my saved delivery details" (phone + zila/upazila/addressLine shown disabled, filled from the account) vs. "Deliver to a new address" (fields blank and editable, `fullName` always stays editable either way since the recipient can differ from the account holder). Picking "new address" reveals a "Save this phone number and address for next time" checkbox, checked by default; on a successful order it fire-and-forgets `PATCH /api/auth/profile` (phone only, name left untouched) then `PATCH /api/auth/delivery-location`, and pushes the result into `useAuthStore` — same non-blocking convention as the app's other post-success side effects (analytics, emails), so a failure here never surfaces as a checkout error. A first-time customer with no saved location just sees the plain editable form with the same save checkbox, defaulting the account's very first save.
- **"Ask someone else to pay"**: `SharedCart` is a cart snapshot (`items: [{product, quantity}]` + who created it), not an order — `POST /api/shared-carts` (needs login) creates one from the current cart and hands back a shareable `/pay/<id>` URL; `GET /api/shared-carts/:id` (public) is what that page reads. Opening the link shows the items to anyone (no login needed to just look), but "Continue to checkout" replaces the *viewer's own* cart with the shared items and sends them through the normal `/checkout` flow logged in as themselves — completing it sets `fulfilledBy`/`fulfilledOrder` on the `SharedCart` so the link shows "already paid for" afterward. This only works because checkout is COD; there's no real payment to route to a third party.
- Cart items now carry `deliveryFeeInsideCity`/`deliveryFeeOutsideCity` (captured at add-to-cart time, same trust model as `price`/`name`/`image` already being client-cached) — `lib/delivery.ts#calculateDeliveryTotal(items, zila)` sums them once the checkout zila is picked.
- **Payment methods**: `Order.paymentMethod` is `"cod" | "bkash"`. `"cod"` always works; `"bkash"` only once the server's `BKASH_*` env vars are set (`orderController.ts`'s `liveOnlinePaymentMethods()` — `createOrder` 400s on `"bkash"` otherwise, same message as every not-yet-live method used to get). Nagad and card, previously shown as disabled "coming soon" placeholders, were removed outright (schema, API, and UI) rather than kept as dead options once the decision was made to launch on Cash on Delivery + bKash only.
- **bKash integration** (`server/src/integrations/bkash.ts`) — Tokenized Checkout (URL-based), the flow bKash's own docs call "Checkout (URL)". Endpoint shapes here were verified directly against bKash's live sandbox, not just its docs, which are internally inconsistent: the "Request URL" headings for Execute/Query describe `paymentID` as a URL path segment, but that actually 403s (a misleading AWS API Gateway `IncompleteSignatureException`, not a real bKash error) — the sample requests further down the same docs, and this file, use `paymentID` in the JSON body to a fixed path instead.
  - **Grant Token** is re-requested (not refreshed) whenever the cached one is near its ~1-hour expiry — bKash's Refresh Token API is rate-limited to twice an hour, while re-granting isn't, so this sidesteps that limit entirely rather than tracking it.
  - **Create Payment** happens *after* `createOrder`'s Mongo transaction commits, never inside it — it's an external network call, and a transaction should never hold open across one. `callbackURL` is this server's own `/api/orders/bkash/callback`, verified live to come back byte-for-byte with `?paymentID=&status=&signature=` appended (not rewritten to some fixed path bKash's docs' one under-specified example implied).
  - **The callback** (`orderController.ts#bkashCallback`, public — bKash redirects the customer's own browser here, it's never called server-to-server) looks the order up by the `bkashPaymentID` stored on it at creation, not by anything in the URL bKash controls beyond that. `status !== "success"` (failure or cancel) cancels the order and restores stock, same as any other cancellation. `status === "success"` calls Execute Payment; if that doesn't come back `"Completed"` (e.g. a repeat hit of this same callback landing on bKash's one-execution-per-paymentID limit instead of a real result), it falls back to Query Payment before deciding. Either way it redirects the browser on to `${CLIENT_URL}/checkout/bkash-result?status=...&order=...` — the frontend's own vocabulary (`success`/`failed`/`cancelled`/`error`), not bKash's raw one.
  - `views/CheckoutView.tsx` doesn't clear the cart or show "order placed" for a `bkash` order — it redirects to `bkashRedirectUrl` immediately, and `views/BkashResultView.tsx` (the page the callback lands on) only clears the cart once `status=success` actually comes back. A failed/cancelled payment leaves the cart untouched, since nothing was charged and the order was already cancelled server-side — there's still something to retry checkout with.
  - `server/.env`'s `BKASH_*` values are bKash's own published **sandbox** test credentials (freely handed out at developer.bka.sh, not secret) — test money only. Swap all five (plus `BKASH_BASE_URL`) for real merchant credentials before going live; nothing else needs to change.
- **Stock is decremented atomically, inside a transaction.** `createOrder`/`adminCreateOrder` run their whole price/stock/order-creation sequence inside a `mongoose.startSession().withTransaction(...)` block. The actual decrement is a single conditional update per line — `Product.updateOne({_id, stock: {$gte: quantity}}, {$inc: {stock: -quantity}})` — not a separate read-then-write, so two concurrent checkouts for the last unit of a product can't both succeed: only one conditional update matches, the other throws and the transaction (including any earlier lines already decremented in the same order) rolls back cleanly. This closed a real overselling race that existed in the original read-then-decrement version.
- **Order cancellation restores stock, exactly once.** A customer can self-cancel their own order via `PATCH /api/orders/:id/cancel` while it's still `"pending"` (not once it's `paid`/`shipped` — at that point it's no longer purely the customer's call). An admin's `PATCH /api/orders/:id/status` restores stock the same way when a status change lands on `"cancelled"` from anything else — both paths share one `restoreStock` helper, and both check the *previous* status wasn't already `"cancelled"` first, so re-sending the same status can't double-restore.
- **Manage Orders** (`views/AdminOrdersView.tsx`, gated by `orders:manage`): every order, filterable by status and searchable by id/name/phone, each row expandable for the full item/address/total breakdown. A `<select>` moves an order through the natural pipeline (`pending → paid → shipped → delivered`, or `cancelled`) via `PATCH /api/orders/:id/status` — deliberately not a strict state machine, since real handling has exceptions (e.g. straight to `cancelled`).
  - **"New order"** (`AdminOrderFormModal.tsx`) records a phone/walk-in order on a customer's behalf: `POST /api/orders/admin` (`adminCreateOrder`) reuses the exact same server-authoritative pricing/stock logic as the real checkout (`createOrder` and `adminCreateOrder` both call a shared `computeOrderTotals` helper) but doesn't require a buyer account — `Order.user` is optional, and a manual order simply never shows up in anyone's "My Orders". Unlike checkout, `adminCreateOrder` accepts any `paymentMethod` (not just `"cod"`) since the admin is recording how a phone customer actually paid (possibly outside the site, e.g. a personal bKash transfer), not triggering a live charge. `Order.source` (`"online" | "manual"`) marks which path created it.
  - **Printing**: each order has a "Print" link to `app/(protected)/admin/orders/[id]/print`, a plain packing-slip/invoice layout (`views/OrderPrintView.tsx`) with a "Print" button calling `window.print()` — this uses the browser's own print dialog (works with whatever printer, thermal or otherwise, the device already has set up) rather than any direct hardware/thermal-printer protocol integration. `print:hidden` on `DashboardSidebar`'s chrome keeps the printed page to just the slip.
  - `GET /api/orders/:id` (`getOrderById`) is used by the print view and is now actually permission-checked (owner of the order, or `orders:manage`) — it previously had no ownership check at all (any signed-in user could fetch any order by id), a bug fixed while building this.

## Auth

One source of truth: `controllers/useAuthStore.ts` (zustand + a `token`/`user` cookie pair). Everything else — the axios interceptor in `lib/api.ts`, the Navbar, `useRequireAuth` — reads from it. Two ways to fill it:

- **Email/password** — `AuthModal` calls the Express API directly (`/api/auth/register`, `/api/auth/login`) and puts the resulting JWT/user straight into the store via `setAuth`.
- **OAuth (Google only** — Facebook sign-in was removed; it never had real credentials wired up in production, see `docs/PROGRESS.md`**)** — handled by [NextAuth.js](https://authjs.dev) v5 (`frontend/src/lib/auth.ts`), but NextAuth's own session is never used directly by the rest of the app. Its `jwt` callback calls the backend's `POST /api/auth/oauth-sync` server-to-server (authenticated with a shared `INTERNAL_API_SECRET` header — the endpoint 403s without it, so it can't be hit from a browser) to find-or-create a real row in the `users` collection and mint one of our own JWTs. `controllers/useOAuthBridge.ts` (mounted once in `app/providers.tsx`) watches `useSession()` and feeds that backend token/user into `useAuthStore` the moment it appears — from that point on OAuth and email/password users are indistinguishable to the rest of the app. `controllers/useAuthController.ts` is now a thin wrapper: it reads `useAuthStore` and, on logout, also calls NextAuth's `signOut()` so a lingering OAuth session cookie doesn't silently re-trigger the bridge and log the user back in.
- The `User` model (`server/src/models/User.ts`) has `password` required only when `provider === "local"`; OAuth users store `provider`/`providerId`/`image` instead.
- Real Google OAuth app credentials (`AUTH_GOOGLE_ID`/`SECRET` in `frontend/.env.local`) are already live in production. `server/.env`'s `INTERNAL_API_SECRET` must match `frontend/.env.local`'s.

### Email verification & password reset

Both share one pattern (`server/src/utils/authTokens.ts`): generate a random 32-byte token, store only its SHA-256 hash on the `User` document (`emailVerificationTokenHash`/`resetPasswordTokenHash`, both `select: false`) with an expiry, and email the raw token in a link — a database leak alone can never be used to verify an email or reset a password, same principle as never storing a plaintext password. Both are sent via the same `utils/sendEmail.ts` already used for the contact form and the welcome email — nothing new to configure once real `RESEND_API_KEY`/`EMAIL_FROM` values exist (see `server/.env.example`), and every send is fire-and-forget (`.catch(console.error)`, one retry on failure) so a down/unconfigured mail provider never blocks or fails the request that triggered it.

**`sendEmail.ts` sends via [Resend](https://resend.com)'s HTTPS API, not raw SMTP.** It started as nodemailer/SMTP direct to Namecheap Private Email, which worked in local development and even in production once — but turned out to be a hard, consistent connection timeout (`ETIMEDOUT` at the raw TCP-connect stage) from Railway specifically, regardless of port (465 or 587 both failed identically), almost certainly one side blocking the other's outbound network path. Since that's not something fixable from inside this codebase, and HTTPS to a well-known API host doesn't have the same class of problem, every email send was moved to Resend's API instead — same fire-and-forget shape, same call sites, no changes needed anywhere except `sendEmail.ts` itself. `EMAIL_FROM` must be on a domain verified in Resend's dashboard (SPF/DKIM records they provide — if the domain already has an SPF record for another provider, merge Resend's `include:` into it rather than adding a second `v=spf1` TXT record, since only one is allowed per domain).

- **Verification**: `User.isEmailVerified` defaults to `true` for OAuth accounts (Google/Facebook already proved the address) and `false` for a local signup. `register` sends a `${CLIENT_URL}/verify-email?token=...` link (24h expiry); the page (`views/VerifyEmailView.tsx`) posts the token to `POST /api/auth/verify-email` on mount — no login required, since a brand-new signup may be opening the link on a different device/browser with no session. `POST /api/auth/resend-verification` (authenticated) re-sends with a fresh token, invalidating the old one — this endpoint used to `await` the send directly instead of firing it and returning, so a slow/unreachable mail provider hung the request and then 500'd; fixed to match every other call site's fire-and-forget shape. `views/EmailVerificationBanner.tsx`, shown on every page under `(protected)`, is the only enforcement today — **nothing is actually blocked** for an unverified account; it's a reminder + one-click resend, not a hard gate. A real gate (e.g. blocking checkout) would need its own decision once email delivery is confirmed reliable, so a down mail provider doesn't lock out every customer.
- **Password reset**: `POST /api/auth/forgot-password` (public) always responds with the same generic message regardless of whether the email matches an account — prevents using it to check who has an account. A match gets a `${CLIENT_URL}/reset-password?token=...` link (1h expiry); `POST /api/auth/reset-password` (public) verifies the token, sets the new password (the `User` schema's existing `pre("save")` hook hashes it, same as `changePassword`), clears the token, and returns a fresh JWT — the reset link having proven control of the inbox is treated as sufficient to also sign them in, rather than making them log in again right after. Only `provider === "local"` accounts are matched (an OAuth account has no password here to reset).

## Roles & permissions (RBAC)

Three roles on `User.role`: `"user"` (default), `"coadmin"`, `"admin"`.

**There is exactly one admin, always.** `"admin"` is not an assignable value in `PATCH /api/users/:id/access` (`userController.ts`'s `ASSIGNABLE_ROLES` is just `["user", "coadmin"]`, and the request 400s if you try) or in `AdminUsersView`'s role dropdown for anyone else's row. The only way admin status moves is `npm run promote-admin -- <email>` in `server/`, which *transfers* it — it demotes any existing admin to `"user"` in the same run, so the DB can never end up with two.

- **`admin`** implicitly holds every permission — there is no way to limit an admin.
- **`coadmin`** holds only whatever is in their `User.permissions` array, drawn from the fixed list in `server/src/utils/permissions.ts` (mirrored in `frontend/src/models/index.ts`'s `ALL_PERMISSIONS`): currently `"products:manage"`, `"orders:manage"`, `"banners:manage"`, `"promotions:manage"`, `"analytics:manage"`, `"ads:manage"`, `"marketing:manage"`, `"messages:manage"`, `"reviews:manage"`.
- **`user`** holds none.

Enforcement is server-side and DB-backed, never trusting the JWT's `role` claim beyond identity:

- `middleware/auth.ts#adminOnly` — full admin required. Re-fetches the user from the DB on every request (not just decoding the JWT), so a demoted admin is blocked immediately rather than at token expiry. Reserved for `routes/userRoutes.ts` (granting/revoking roles and permissions) — **intentionally not delegable to coadmins**, so a coadmin can never escalate their own or anyone else's access.
- `middleware/auth.ts#authorize(permission)` — admin, or a coadmin holding that specific permission. Same DB-freshness guarantee. Used on the product/order write routes (`routes/productRoutes.ts`, `routes/orderRoutes.ts`) in place of the old blanket `adminOnly`.

Frontend mirrors this only for UI gating (hide/show), never as real enforcement — the API is the source of truth:

- `controllers/useAuthController.ts#hasPermission(permission)` — same admin-bypass logic, for conditionally rendering admin-only controls.
- `controllers/useRequireAdmin.ts` — client-side redirect (like `useRequireAuth`, same "no SSR check yet" caveat) guarding `app/(protected)/admin/users/page.tsx` → `views/AdminUsersView.tsx`, where an admin assigns roles/permissions to other users via `services/userService.ts` (`GET /api/users`, `PATCH /api/users/:id/access`).

**Bootstrapping the first admin:** every new account (email/password or OAuth) starts as `role: "user"`, and only an existing admin can promote someone — so the very first admin can't be created through the app. Run `npm run promote-admin -- <email>` in `server/` once to promote an existing account directly in the DB.

## Image uploads

Every image upload in the app — product photos, banner images, ad images, profile pictures — goes through one shared path: `upload` (multer, configured with `memoryStorage()` in `utils/upload.ts`, so a file only ever exists as an in-memory buffer, never multer-managed disk state) as the route middleware, then `await storeUploadedFile(file)` in the controller to actually persist it and get back the URL to save on the document. No controller reads `file.filename`/`file.path` directly.

- **Same "zero-config-required, falls back until keys are added" pattern as SMS/ads/Sentry** (`utils/cloudinary.ts#isCloudinaryConfigured`): with `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` unset (the default — see `server/.env.example`), `storeUploadedFile` writes the buffer to `server/uploads/<uuid>.<ext>` and returns that local path, exactly what this app always did. Once all three are set, it instead uploads to Cloudinary and returns its permanent `secure_url` — no other code changes anywhere, since every consumer of a stored image path already treats it as an opaque string.
- **Old and new images coexist with zero migration**: the frontend's `lib/api.ts#toUploadUrl` and the ad integrations' `adController.ts#toPublicImageUrl` both already pass an absolute URL through unchanged and only prefix a bare local path with the right origin — so a product with some images uploaded before Cloudinary was configured and some after displays and posts correctly either way, no backfill needed.
- **Why this matters**: a local-disk upload doesn't survive a redeploy on most hosting platforms (the filesystem isn't guaranteed persistent), which would silently delete every product/banner image ever uploaded. Moving to real object storage is the standard fix — Cloudinary specifically (over generic S3-style storage) was picked because it's purpose-built for images (automatic format/size optimization on top of just storing the file) and its free tier comfortably covers a store this size.

## Social media ads

`views/AdminAdsView.tsx` (gated by `ads:manage`) generates an ad's content from a product, an active promo code, or a fully custom event, and can post it directly to Facebook, Instagram, and X from the server — no manual copy-pasting into each platform's own composer.

- **Ad model** (`server/src/models/Ad.ts`): `title` (internal only), `sourceType` (`"product" | "promotion" | "custom"`, just a badge — doesn't gate anything), optional `product`/`promoCode` refs, `caption`, `image` (a normal `/uploads` path, same convention as Product/Banner), `link`, the `platforms` it targets, and a `results` array — one entry per platform with a `status` (`"pending" | "posted" | "failed" | "not_connected"`), `externalPostId`, and `errorMessage`. `AdminAdFormModal.tsx` auto-fills title/caption/link from whichever product or promo is picked (editable afterwards); the image falls back to that product's own first photo if nothing is uploaded, server-side (`adController.ts#createAd`), so re-uploading an already-hosted photo is never required.
- **Publishing** (`POST /api/ads/:id/publish`, optional `{platforms}` to retry just one) calls each platform's connector and writes the outcome straight onto the ad's `results` — one platform failing (or not being connected) never stops the others, and every attempt's result is real, not just "queued". This is the "keep track of every ad generated and run from the site" system: the list at `/admin/ads` is the log, not a separate audit trail.
- **Facebook + Instagram** (`server/src/integrations/meta.ts`) both post through Meta's Graph API using one Page access token (`FACEBOOK_PAGE_ID`/`FACEBOOK_PAGE_ACCESS_TOKEN`/`INSTAGRAM_BUSINESS_ACCOUNT_ID` — see `server/.env.example`). A single self-owned Page/app can use these **without Meta's App Review** by adding your own accounts as "testers" on the Facebook Developer app. Instagram publishing is always a two-step create-container-then-publish call and always needs an image (no text-only IG post exists) — that image has to be a real public https URL, since Meta's servers fetch it directly; `SERVER_PUBLIC_URL` (also in `.env.example`) is what turns a stored `/uploads/...` path into one, and it needs to be the server's actual public domain once deployed, not `localhost`. Once Cloudinary is configured (see "Image uploads" below), a new ad's `image` is already a real public https URL on its own — `SERVER_PUBLIC_URL` then only matters for images still stored locally from before that switch.
- **X** (`server/src/integrations/x.ts`) posts text (with the link appended) via `POST /2/tweets`, hand-signed with OAuth 1.0a (`X_API_KEY`/`X_API_SECRET`/`X_ACCESS_TOKEN`/`X_ACCESS_SECRET`) rather than a library, so there's no new dependency for one endpoint. **Posting requires a paid X API tier** as of X's current pricing — the signing code is correct, but this is the one integration that costs money to actually turn on. Image tweets aren't wired up (X's media upload is a separate v1.1 multipart endpoint) — text + link only.
- Every connector has an `isXConfigured()`-style check; publishing a platform with no keys set records `"not_connected"` immediately rather than attempting (and failing) a real API call — the whole feature works today with zero keys configured, it just shows everything as "Not connected" until real credentials are added.

## Marketing campaigns (email/SMS)

Reaches customers directly by email/SMS using the contact info already collected at signup (`User.email`) and at checkout/Settings (`User.phone`, see "Checkout & Orders" above) — opt-in only, gated by the new `marketing:manage` permission (delegable to coadmins like every other admin section) at `/admin/campaigns` (`views/AdminCampaignsView.tsx`).

- **Opt-in, never on by default**: `User.marketingOptIn: { email: boolean; sms: boolean }` (`server/src/models/User.ts`). `PATCH /api/auth/marketing-opt-in` (`updateMarketingOptIn`) flips either flag — it 400s on enabling `sms` without a `phone` already on the account, so a campaign send can never end up with a "true" flag and nothing to send to. Two places set it: Settings' "Promotions" section (`views/SettingsView.tsx`'s `MarketingSection`, both channels) and a "Send me SMS about offers" checkbox on `/checkout` (only shown once a phone number naturally exists on the form, and only if not already opted in) that fires the same PATCH non-blockingly after a successful order — same convention as checkout's save-delivery-address side effect.
- **`Campaign` model** (`server/src/models/Campaign.ts`): `sourceType` (`"product" | "promotion" | "custom"`, a badge only, mirrors `Ad.sourceType`), optional `product`/`promoCode` refs, `channels: ("email"|"sms")[]`, the actual `emailSubject`/`emailBody`/`smsMessage` content, a `stats` snapshot (`recipientCount`/`sentCount`/`failedCount`, kept as a cheap-to-read header even once `recipients` below has hundreds of entries), and `recipients: {user, name, channel, status, error}[]` — one entry per (recipient × channel actually attempted), embedded rather than a separate collection since a campaign's recipient list is only ever read alongside the campaign itself and this store's scale keeps it well within Mongo's 16MB document limit. `views/AdminCampaignsView.tsx`'s `CampaignRow` expands to show this list.
- **Composing and sending are the same step** — unlike social ads (draft, then publish separately), `POST /api/campaigns` (`createCampaign`) both creates the `Campaign` document and sends immediately: it queries `User` for whoever has `marketingOptIn.email`/`.sms` true (and, for SMS, a non-empty `phone`), fires `sendEmail`/`sendSms` at each (each recipient's own try/catch, so one failure never stops the rest), and records both the aggregate counts and the per-recipient log. `AdminCampaignFormModal.tsx` (mirrors `AdminAdFormModal.tsx`) auto-fills a starting subject/body/SMS text from a picked product or active promo code (freely editable after), and `GET /api/campaigns/audience` (`getAudiencePreview`) shows the admin how many people are actually opted into each channel, and whether SMS is even connected, before they hit send — the send itself is behind the app's in-app `confirmDialog` ("This can't be undone"), not a native `window.confirm`. There's still no scheduling — sending is always immediate.
- **One-click unsubscribe**: every campaign email gets a per-recipient footer link (`utils/campaignTokens.ts#generateUnsubscribeToken`) — an HMAC-SHA256 of the user's id keyed on the existing `JWT_SECRET`, not a new stored/expiring token like `authTokens.ts`'s email-verification flow. `GET /api/auth/unsubscribe?uid=&token=` (public, no login) recomputes the HMAC and compares with `crypto.timingSafeEqual`; a match flips `marketingOptIn.email` to `false` only (never SMS, never the account itself). `app/(public)/unsubscribe/page.tsx` → `views/UnsubscribeView.tsx` is the landing page, mirroring `VerifyEmailView.tsx`'s checking/success/error states.
- **Email** reuses the existing `utils/sendEmail.ts` (Resend's API) already used for verification/reset/contact emails — same "fails silently, non-blocking, works the moment real `RESEND_API_KEY`/`EMAIL_FROM` env vars exist" story as those.
- **SMS** (`server/src/integrations/sms.ts`) is a generic HTTP-based sender, not a specific vendor SDK — Bangladeshi bulk-SMS gateways (BulkSMSBD, MimSMS, SSL Wireless, Alpha SMS, etc.) each have their own request shape, so this targets the single most common pattern (HTTP GET/POST with `api_key`/`senderid`/`number`/`message`) configured entirely through `SMS_API_URL`/`SMS_API_KEY`/`SMS_SENDER_ID`/`SMS_METHOD` env vars (see `server/.env.example`) — a gateway that doesn't match this shape only needs that one file adjusted, nothing else in the app changes. `isSmsConfigured()` gates the audience preview's "SMS not connected yet" hint; with no keys set, every SMS send just fails and gets counted, the same zero-config-required story as the ads integrations.

## Reviews, wishlist, and categories

- **Verified purchase**: `Review.isVerifiedPurchase` (`server/src/models/Review.ts`) is computed once, at submit time (`reviewController.ts#submitReview`) — `Order.exists({user, status: "delivered", "items.product": productId})`. A snapshot, not a live join: a later cancellation/refund never retroactively changes an already-submitted review's badge. Shown as a small badge next to the reviewer's name in `views/ProductReviews.tsx`.
- **Review moderation**: new `reviews:manage` permission (delegable, same pattern as every other admin section). Anyone holding it sees an inline delete (trash icon) on every review across every product — there's no separate "Manage Reviews" admin page, since moderation here means removal, not editing, and doesn't need its own listing screen the way Products/Orders do.
- **Wishlist "move to cart"**: Dashboard's "Saved items" section adds every saved product to the cart (`useCartStore.addItem`) and then removes it from the wishlist (`useWishlistStore.toggle`) — a real move, not a copy, so revisiting the dashboard doesn't keep re-offering items already in the cart.
- **Category matching is case-insensitive**, not a separate `Category` collection (`Product.category` is still free text). `getProducts`' `?category=` filter uses a case-insensitive exact-match regex; `getProductCategories` groups by lowercased category, picking the oldest matching product's original casing as the display label (deterministic via `$sort` before `$group`, not whatever order Mongo happens to return). This fixes "Shoes" and "shoes" showing as two categories without a schema migration — a genuinely separate Category collection (own slug/image/admin CRUD) remains a bigger, separate project if dedicated category management is ever wanted.

## Admin dashboard overview

`/dashboard` shows one of two different things depending on who's looking (`views/DashboardHome.tsx`, a small client-side dispatcher rendered by the page): an admin, or a coadmin holding `orders:manage` and/or `products:manage`, gets `views/AdminDashboardOverview.tsx` — pending-order count, total orders, revenue, total products, and a low-stock (`stock <= 5`) list — instead of the plain customer "my orders" view (`DashboardOverview.tsx`). A coadmin with neither permission still falls back to the customer view, since a blank overview would be worse than none.

This is deliberately *not* the same data source as the full Analytics page — `GET /api/orders/stats` (`orderController.ts#getOrderStats`) and `GET /api/products/stats` (`productController.ts#getProductStats`) are lightweight, single-purpose endpoints gated by `orders:manage`/`products:manage` respectively, not `analytics:manage`. An orders-only or products-only coadmin gets a useful home screen without needing the (separate, heavier) analytics grant. Revenue uses the same definition as `analyticsController.ts` (`paid`/`shipped`/`delivered` orders only), and the low-stock threshold matches it too — kept in sync by convention, not a shared constant, since one is an all-time snapshot query and the other is folded into a bigger aggregate pipeline.

## Contact messages (admin inbox)

`ContactMessage` gained an `isRead` boolean (default `false`) purely for admin-side triage — never shown to or settable by the sender. `/admin/messages` (`views/AdminMessagesView.tsx`, gated by the new `messages:manage` permission) lists every message newest-first, expands to the full body plus a `mailto:` "Reply by email" link (there's no in-app reply/thread system — this is a small store, and the sender's own inbox is the right place for a back-and-forth), a mark read/unread toggle, and delete. This exists because previously the *only* way to see a submitted message was the best-effort `CONTACT_EMAIL` notification, which doesn't arrive at all until real mail-provider credentials are configured (see the email-verification section above) — the message was always saved to the database regardless, just unreadable without querying it directly.

## Analytics

`AnalyticsEvent` records two event types fired fire-and-forget from the storefront (`lib/analytics.ts`, mounted once via `usePageViewTracking` in `app/providers.tsx`): `page_view` and `product_click`. A per-browser `sessionId` (random, `localStorage`-persisted, not tied to login) is how anonymous "unique visitors" get counted at all. `/admin/*` routes are excluded on purpose — an admin browsing their own panel isn't storefront traffic.

- **Retention**: a MongoDB TTL index (`{createdAt: 1}, {expireAfterSeconds: 180 days}`) auto-deletes events past that age on Mongo's own background sweep — no cron job or manual cleanup needed. 180 days comfortably covers the dashboard's longest preset (`30d`); `"all"` just means "everything still within the retention window," not literally forever.
- **Manual reset, full-admin only**: `views/AdminAnalyticsView.tsx`'s "Reset analytics data" section lets an admin permanently delete `AnalyticsEvent` history on demand — useful for clearing out dev/test traffic right before a real launch, without waiting 180 days for the TTL index. Filtered, not all-or-nothing: checkboxes for which field(s) to include (`page_view`, `product_click` — the only two real fields, since every stat on the dashboard derives from one of them) and an age cutoff (all time / older than 30d / older than 7d / before today), both narrowing a shared `buildEventFilter()` used identically by a count-preview endpoint (`GET /api/analytics/events/count`) and the actual delete (`DELETE /api/analytics/events`) — so the number shown in the confirm dialog is always exactly what gets deleted, and a 0-match filter short-circuits before ever opening that dialog. Gated by `adminOnly` (not `authorize("analytics:manage")`) and hidden from the UI entirely unless `user.role === "admin"` — deliberately not delegable to a coadmin, even one holding `analytics:manage`, since permanently deleting history is a different order of consequence than just viewing it. Only ever touches `AnalyticsEvent` — products/orders/users/revenue are untouched, verified live.

- **Traffic source ("Visitors by source")**: each tracked event also carries the browser's `document.referrer` at the moment it fired. A full-page load's referrer is fixed for the whole tab — client-side route changes don't update it — so a session's *first* `page_view` is the one that reflects where that visitor actually came from. `getAnalyticsOverview` groups events by `sessionId`, takes the first (by `createdAt`) referrer per session, and classifies each via `utils/referrer.ts#classifyReferrer` — a hostname match against known social domains (Facebook, Instagram, WhatsApp, Messenger, Telegram, X/Twitter, LinkedIn, YouTube, TikTok, Pinterest), falling back to `"Other websites"` for an unrecognized referrer or `"Direct / App"` for none. This is best-effort: some in-app browsers (mobile Facebook/Instagram especially) blank or rewrite the referrer, so it undercounts rather than overcounts.
- All of this is one consolidated `GET /api/analytics/overview` payload (gated by `analytics:manage`) rather than several endpoints, rendered by `views/AdminAnalyticsView.tsx`'s reusable `BarList`/`StatTile` pieces.
- **Date range**: `?range=today|7d|30d|all` (default `"30d"`), resolved server-side by `utils/analyticsRange.ts#resolveAnalyticsRange` into a `createdAt` cutoff applied to orders, traffic, and product-click data — the time-series-shaped numbers. Product/user totals (stock, categories, roles, sign-in methods) are always "as of now" regardless of range; there's no meaningful "stock count for the last 7 days," so those queries never take the filter. The response echoes back the resolved `{ preset, from, to }` so the dashboard can show the actual window rather than just the preset's name — useful since `"today"` depends on the server's clock/timezone, not the browser's.

## Reliability & security hardening

Backend-focused, since that's where a real outage or abuse would actually happen — see `docs/REMAINING_WORK.md`'s Priority 3 for the full list and what's still open.

- **Rate limiting** (`middleware/rateLimit.ts`, `express-rate-limit`): `authLimiter` (20 requests/15 min per IP) on every auth endpoint that doesn't already require being logged in — register, login, forgot-password, reset-password, resend-verification — and `contactLimiter` (5/hour per IP) on the public contact form, the one endpoint on the whole site with zero authentication at all. Both are IP-keyed rather than account-keyed, since an unauthenticated request has no account to key off yet.
- **Security headers** (`helmet`, in `app.ts`): `contentSecurityPolicy` is explicitly disabled — this server is a JSON API plus a static `/uploads` folder, not an HTML-serving app, so a page-oriented CSP isn't meaningful here and risks blocking something unexpectedly. `crossOriginResourcePolicy` is relaxed to `"cross-origin"` — helmet's default `"same-origin"` would otherwise make the browser refuse to render product/banner images, since the frontend loads them from this server's different origin.
- **Error monitoring** (`utils/errorMonitoring.ts`): the same "zero-config-required, shows as not connected until keys added" pattern as the SMS/social-ads integrations. `reportError()` always `console.error`s (so local dev never loses visibility) and *also* reports to Sentry once `SENTRY_DSN` is set — nothing else in the app needs to change when that happens. Wired into the global Express `errorHandler` and into two process-level handlers in `server.ts`.
- **Process-level crash handling** (`server.ts`): `uncaughtException`/`unhandledRejection` handlers report the error and then `process.exit(1)` deliberately, rather than let the process keep serving requests in an undefined state (Node's own guidance) — this pairs with `ecosystem.config.js` below, since exiting only helps if something then restarts it. Note this is the *last-resort* safety net, not the primary error path: Express 5 already auto-forwards a rejected promise/thrown error from any async route handler straight to `errorHandler` instead of crashing the process at all, so a normal request-handling bug never reaches these two handlers in the first place.
- **Process supervision** (`ecosystem.config.js`, PM2): `npm run start:pm2` gives a real, no-external-account way to auto-restart the server if it ever does crash, for a self-managed host (a raw VPS) where nothing else does that. Capped at 10 restarts with a 2s delay and a 10s minimum uptime, so a crash-looping bad deploy backs off instead of hot-looping forever. Redundant (but harmless) on a PaaS that already restarts crashed processes itself.
- **Tests** (Vitest, `server/` and `frontend/`, `npm test` in each): a real baseline around the highest-value logic rather than exhaustive coverage — `orderController.test.ts` covers `computeOrderTotals`'s pricing/delivery-fee/promo-discount math and the atomic stock-decrement logic (see "Checkout & Orders" above) with mocked Mongoose models, plus smaller tests for `analyticsRange`, `referrer`, `authTokens`, and `permissions`. The frontend suite covers the pure money/promo functions in `lib/` (`currency`, `delivery`, `promo`). `.github/workflows/ci.yml` type-checks, lints, and runs both suites on every push/PR — though this repo has no `.git` yet, so CI can't actually execute until it's initialized and pushed to GitHub.
